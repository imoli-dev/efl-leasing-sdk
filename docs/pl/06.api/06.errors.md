## EflLeasingException

[`EflLeasingException`](#eflleasingexception) jest klasą bazową dla wszystkich błędów specyficznych dla SDK.

## Hierarchia wyjątków

Wszystkie błędy specyficzne dla SDK dziedziczą po [`EflLeasingException`](#eflleasingexception):

- [`EflLeasingException`](#eflleasingexception) – klasa bazowa dla wszystkich wyjątków SDK.
- [`ApiException`](#apiexception-and-problemdetails) – błędy na poziomie API (HTTP 4xx/5xx) zwracane przez EFL Leasing Online API.
- [`HttpException`](#httpexception) – błędy na poziomie transportu (awarie sieci, timeouty, nieprawidłowe odpowiedzi).

Zazwyczaj powinieneś unikać przechwytywania ogólnego `\Exception` i zamiast tego przechwytywać te konkretne klasy.

## ApiException i ProblemDetails

[`ApiException`](#apiexception-and-problemdetails) reprezentuje odpowiedź o błędzie z EFL API.
Udostępnia on:

- Kod statusu HTTP (np. 400, 404, 500).
- Instancję [`ProblemDetails`](04.models/44.problem-details.md) ze strukturalnymi informacjami.

```php
use Imoli\EflLeasingSdk\Exception\ApiException;

try {
    $offer = $client->calculateBasicOffer($basket, $token);
} catch (ApiException $e) {
    $statusCode = $e->getStatusCode();
    $details = $e->getProblemDetails();

    // Log the error and return an appropriate response to the caller
}
```

[`ProblemDetails`](04.models/44.problem-details.md) jest zgodny ze strukturą RFC 7807 i zazwyczaj zawiera pola takie jak:

- `type`
- `title`
- `status`
- `detail`
- `instance`

Używaj tych pól do diagnostyki, logowania i monitorowania.

## HttpException

[`HttpException`](#httpexception) reprezentuje awarie w bazowej warstwie HTTP, takie jak:

- Timeouty.
- Problemy z połączeniem sieciowym.
- Nieprawidłowe lub błędnie sformatowane odpowiedzi HTTP.

Powinieneś traktować je jako błędy przejściowe lub infrastrukturalne i decydować, czy ponowić próbę, czy przerwać operację.

```php
use Imoli\EflLeasingSdk\Exception\HttpException;

try {
    $offer = $client->calculateBasicOffer($basket, $token);
} catch (HttpException $e) {
    // Log the transport error and decide whether to retry
}
```

## Najlepsze praktyki

- Przechwytuj [`ApiException`](#apiexception-and-problemdetails) oraz [`HttpException`](#httpexception) na granicach integracji (kontrolery, handlery wiadomości).
- Mapuj błędy API na odpowiednie kody statusu HTTP we własnym API.
- Nie udostępniaj surowych danych `ProblemDetails` bezpośrednio użytkownikom końcowym; zamiast tego loguj szczegółowe informacje i wyświetlaj przyjazne komunikaty.
- Monitoruj częstotliwość i treść tych wyjątków za pomocą systemu śledzenia błędów.
- Używaj pól `ProblemDetails` (`type`, `title`, `status`, `detail`) jako strukturalnych pól logów, a nie tekstu swobodnego.
- Rozważ ograniczoną liczbę powtórzeń tylko dla operacji idempotentnych, które kończą się błędem `HttpException`, i zawsze loguj przyczynę źródłową.
