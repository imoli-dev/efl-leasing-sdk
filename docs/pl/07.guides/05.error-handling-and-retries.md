## Przegląd

Ten przewodnik pokazuje, jak:

- Przechwytywać i obsługiwać wyjątki SDK (`ApiException`, `HttpException`).
- Mapować błędy na własne odpowiedzi API.
- Używać `ProblemDetails` do logowania i diagnostyki.
- Myśleć o ponowieniach i timeoutach w systemach produkcyjnych.

Uzupełnia on informacje referencyjne zawarte w sekcji **Obsługa błędów**.

## Przechwytywanie ApiException i HttpException

Wszystkie błędy specyficzne dla SDK rozszerzają `EflLeasingException`, a dwie najważniejsze podklasy to:

- `ApiException` – błędy na poziomie API (HTTP 4xx/5xx) zwracane przez API EFL Leasing Online.
- `HttpException` – błędy na poziomie transportu (awarie sieci, timeouty, nieprawidłowe odpowiedzi).

```php
use Imoli\EflLeasingSdk\EflClient;
use Imoli\EflLeasingSdk\Exception\ApiException;
use Imoli\EflLeasingSdk\Exception\HttpException;

try {
    $offer = $client->calculateBasicOffer($basket, $token);
} catch (ApiException $e) {
    // API EFL zwróciło strukturalną odpowiedź o błędzie
    $statusCode = $e->getStatusCode();
    $problemDetails = $e->getProblemDetails(); // może być null, jeśli nie zostało dostarczone

    // Zaloguj szczegóły i przetłumacz na błąd specyficzny dla Twojej domeny
} catch (HttpException $e) {
    // Problem na poziomie transportu (timeout, problem z połączeniem, błędnie skonfigurowany klient HTTP)
    // Zdecyduj, czy ponowić próbę, czy szybko zgłosić błąd (fail fast)
}
```

Unikaj przechwytywania `\Exception` w ogólnych handlerach.
Traktuj `ApiException` i `HttpException` jako główną granicę dla awarii związanych z SDK.

## Mapowanie błędów na odpowiedzi Twojego API

Budując własne API HTTP, mapuj wyjątki SDK na odpowiednie odpowiedzi:

- `ApiException`:
  - Użyj kodu statusu HTTP z wyjątku jako punktu wyjścia.
  - Mapuj problemy z walidacją lub naruszenia reguł biznesowych na odpowiedzi 4xx w swoim API.
- `HttpException`:
  - Zazwyczaj mapuj na `503 Service Unavailable` lub `502 Bad Gateway`.
  - Wskaż, że problem jest tymczasowy lub związany z infrastrukturą.

Przykład handlera na poziomie kontrolera:

```php
try {
    $offer = $client->calculateBasicOffer($basket, $token);

    return new JsonResponse($offer, 200);
} catch (ApiException $e) {
    $problem = $e->getProblemDetails();

    // Nie ujawniaj pełnych szczegółów problemu użytkownikom końcowym
    $responseBody = [
        'message' => 'Usługa leasingowa odrzuciła żądanie.',
        'code' => $problem?->getType(),
    ];

    return new JsonResponse($responseBody, $e->getStatusCode());
} catch (HttpException $e) {
    // Ogólny błąd infrastruktury
    return new JsonResponse(
        ['message' => 'Usługa leasingowa jest tymczasowo niedostępna.'],
        503
    );
}
```

## Logowanie i monitoring z ProblemDetails

`ApiException` udostępnia opcjonalną instancję `ProblemDetails`, która jest zgodna z RFC 7807.
Zawiera ona strukturalne pola, takie jak `type`, `title`, `status`, `detail` i `instance`.

Używaj tych pól do logowania i monitoringu:

- Loguj `type`, `title`, `status` i `detail` do swojego scentralizowanego systemu logowania.
- Używaj `instance` lub dodatkowych pól rozszerzeń do korelacji, gdy są dostępne.
- Buduj pulpity nawigacyjne (dashboards) lub alerty na podstawie powtarzających się kombinacji `type`/`status`.

Uważaj, aby nie logować pełnych danych klientów ani innych danych osobowych.
Traktuj `ProblemDetails` jako informacje diagnostyczne, a nie jako komunikaty dla użytkownika.

## Ponowienia i timeouty

Ponowienia (retries) są odpowiednie tylko dla niektórych klas błędów:

- Dobre kandydatury:
  - `HttpException` spowodowane przejściowymi problemami sieciowymi lub timeoutami.
  - Idempotentne żądania GET, takie jak odpytywanie o status lub odczytywanie zmian procesu.
- Złe kandydatury:
  - `ApiException` reprezentujące błędy walidacji lub naruszenia reguł biznesowych.
  - Nieidempotentne żądania POST, które mogłyby stworzyć zduplikowane efekty uboczne.

Typowe podejście:

1. Skonfiguruj rozsądne **timeouty** na poziomie klienta HTTP (zobacz sekcję *Konfiguracja*).
2. Opcjonalnie zaimplementuj prosty mechanizm ponowień wokół wywołań idempotentnych:
   - Użyj wykładniczego czasu oczekiwania (np. 200ms, 400ms, 800ms).
   - Ogranicz liczbę prób.
3. Loguj wszystkie awarie, nawet jeśli ponowienie ostatecznie zakończy się sukcesem.

```php
use Imoli\EflLeasingSdk\Exception\HttpException;

function callWithRetry(callable $operation, int $maxAttempts = 3)
{
    $attempt = 0;
    $delayMs = 200;

    while (true) {
        ++$attempt;

        try {
            return $operation();
        } catch (HttpException $e) {
            if ($attempt >= $maxAttempts) {
                throw $e;
            }

            usleep($delayMs * 1000);
            $delayMs *= 2;
        }
    }
}

$state = callWithRetry(
    fn () => $client->getProcessChanges($transactionId, null, $token)
);
```
